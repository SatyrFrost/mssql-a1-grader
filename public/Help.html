ERD Grader: Automated Assessment Tool for Entity-Relationship Diagrams

 

 

1. Introduction

 

The ERD Grader is a web-based application designed to assist teachers in automatically assessing Entity-Relationship Diagrams (ERDs) created using draw.io (now app.diagrams.net).  Its primary goal is to streamline the grading process for Part 1 of Assignment 1 in the Data Modelling and SQL course.  It can mark the ERD part of the assignment by providing instant, objective feedback on the structural correctness of student submissions.  Students upload their draw.io XML files, and the grader provides a detailed report, including a score out of 40, highlighting areas of correctness and potential errors.

 

 

2. How it Works

 

You can upload each student’s draw.io XML file to the webpage.  The grader then reads the diagram's structure and compares it against a predefined correct ERD model.  It then generates a detailed report and a score.

 

 

3. What it Checks

 

The grader thoroughly evaluates the following aspects of a student's ERD:

 

·        Entities (Tables): It identifies all tables in the diagram.  It's smart enough to recognize table names even with minor spelling differences or pluralization (e.g., "Custumer" vs. "CUSTOMER").  It also notes any missing required tables.

 

·        Attributes (Fields): For each table, it extracts all listed attributes.  It uses similar "fuzzy matching" to account for slight variations in attribute names (e.g., "CustID" vs. "CustomerID").

 

·        Primary Keys (PK) and Foreign Keys (FK): It verifies that the correct attributes are marked as PKs and FKs within each table, matching the expected structure. This includes handling composite keys.

 

·        Relationships and Cardinality:

o   It identifies all connections between tables. Crucially, it can detect connections even if they're drawn to an attribute within a table rather than directly to the table's border, preventing unfair deductions for minor drawing quirks.

o   It checks if all necessary relationships are present and if the cardinality (e.g., "one-to-many", "zero-to-many") at both ends of each relationship is correct.

 

 

4. How it Grades

 

The grading system awards points across three main categories, which are then scaled to a final score out of 40:

 

·        Fields (Attributes): Points are awarded for each correctly identified attribute.

·        Keys (PK/FK): Points are given for each attribute correctly designated as a Primary Key or Foreign Key.

·        Relationships: Points are awarded for correctly identifying relationships between tables and for correctly specifying the cardinality at both ends of each relationship.

 

The report provides a breakdown of marks for each category and a final scaled score.

 

 

5. Limitations

 

It's important to be aware of the grader's current limitations:

 

·        It only works with XML files exported from draw.io.

·        Strict Comparison: It grades against a single, predefined "correct" ERD.  Any valid alternative designs that differ from this model will be marked as incorrect.

·        No Semantic Understanding: It checks the structure, not the meaning.  It can't tell if the ERD accurately represents a real-world scenario, only if it matches the expected blueprint.

·        Visuals Ignored: It doesn't assess the aesthetic layout or clarity of the diagram.

Data Dictionary Builder and Grader: Automated Tool for Grading Data Dictionaries

 

 

1. Introduction

 

The Data Dictionary Builder is a web-based application designed for students to create Data Dictionaries using a web form.  Students need to create a Data Dictionary for Part 2 of Assignment 1 in the Data Modelling and SQL course.  Students will complete the Data Dictionary webform, and then download their work as a JSON file.  This file will allow teachers to automatically grade their work.

 

The Teacher Grading Page is a separate page only available for teachers.  It allows teachers to upload the students’ Data Dictionary JSON files, and the page will automatically grade their work.  The grader provides a detailed report, including a score out of 15, highlighting areas of correctness and potential errors.

 

 

2. How it Works

 

Data Dictionary Builder

 

This page is an interactive tool where students can create and manage their Data Dictionaries. They can:

 

·        Add new tables and define their names.

·        For each table, they can add, edit, and remove columns.

·        For each column, they can specify details like its name, data type (e.g., VARCHAR, INT), size, whether it's a primary key or foreign key, if it's optional, if it auto-increments, its default value if necessary, and a description.

·        They can save their work to their browser's local storage, load previously saved data, download their data dictionary as a JSON file, or clear all their entries to start fresh.

 

 

Teacher Grader Page

This page is designed for teachers to evaluate student submissions of data dictionaries.  Students cannot access this page.  Here are its capabilities:

 

·        It allows teachers to upload a student's Data Dictionary (in JSON format).

·        It allows teachers to grade each student's submission by comparing it against a pre-defined "model answer" Data Dictionary.

·        It provides a detailed breakdown of the grading results, showing scores for correctly identified keys, fields, data formats, sizes, and descriptions.

·        Teachers can view both the student's uploaded data dictionary and the reference model answer for comparison.

·        This page is protected and requires a teacher password to access.

 

 

The grader thoroughly evaluates the following aspects of a student's Data Dictionary:

 

1.     Table Matching:

 

·        It first tries to match each table in the reference data dictionary to a table in the student's submission.

·        It uses a "fuzzy matching" approach, meaning it doesn't require an exact name match. It normalizes table names (converts to lowercase, removes spaces and underscores) and then calculates a similarity score. If the similarity is above a certain threshold (0.7), it considers it a match.

 

 

2.     Column Matching:

 

·        Once a reference table is matched to a student table, the grader then attempts to match each column within that reference table to a column in the student's matched table.

·        Similar to table matching, it uses fuzzy matching for column names (normalizing names and checking for similarity above a 0.5 threshold). It also accounts for simple pluralization (e.g., "car" vs "cars").

 

 

3.     Field Score (1 point per matched column):

 

·        If a reference column is successfully matched to a student column, the student receives 1 point for that field.

 

 

4.     Data Type Check (1 point per matched data type):

 

·        For each matched column, it checks if the dataType (e.g., VARCHAR, INT) in the student's submission exactly matches the reference.

 

5.     Size and Auto-increment Check (1 point per matched size/auto-increment status):

 

·        It verifies the size and isAuto (auto-incrementing) properties.

·        For VARCHAR types, it's flexible: any positive size is accepted as long as the isAuto status matches.

·        For other data types, the size must match exactly, and the isAuto status must also match.

·        A special case is handled for auto-incrementing primary keys where the size is typically null in the reference; the student's submission must reflect this.

 

 

6.     Primary Key (PK) Check (1 point per correctly identified PK):

 

·        It checks if the isPrimaryKey status of the student's column matches the reference. A point is awarded for each correct identification.

 

7.     Foreign Key (FK) Check (1 point per correctly identified FK):

 

·        It checks if the isForeignKey status of the student's column matches the reference. A point is awarded for each correct identification.

 

8.     Description Check (0.5 points per provided description):

 

·        It checks if the columnDescription field in the student's submission is provided and not empty. If a description is present, 0.5 points are awarded.

Finally, all these individual scores are summed up to give a total raw score, which is then converted to a final mark out of 15. The grader also provides detailed feedback for each check, indicating whether it passed or failed.

SQL Grader: Automated Tool for Grading SQL

 

 

1. Introduction

 

This application, "SQL Grader for Teachers," is a web-based tool designed to help teachers automatically grade student-submitted SQL files for Assignment 1: Parts 3 and 4.

 

Students will write their SQL and upload an .sql file or .txt file.  Teachers will upload the students’ .sql files or .txt files, and the page will automatically grade their work.  The grader provides a detailed report, including a score out of 45, highlighting areas of correctness and potential errors.

 

 

2. How it Works

 

This page is designed for teachers to evaluate student submissions of their SQL code.  Students cannot access this page.  Here are its capabilities:

 

·        It allows teachers to upload a student's SQL file (in .sql file or .txt file format).

·        It allows teachers to grade each student's submission by comparing it against a pre-defined "model answer" SQL.

·        It provides a detailed breakdown of the grading results, evaluating the structural correctness and adherence to specific requirements for table definitions, and then it assesses the success rate of data insertion statements.  The total score is the sum of marks from both sections.

·        This page is protected and requires a teacher password to access.

 

 

3. What it looks for (Specific Criteria/Checks):

 

For CREATE TABLE Statements:

 

·        Tables: Checks for the existence of specific tables (e.g., Colour, Customer, Car, Sale, Orders, etc.), even with fuzzy name matching (e.g., Colors maps to Colour).

·        Primary Keys (PK): Awards marks for correctly defined primary keys.

·        Identity Columns: Checks for the presence of IDENTITY columns (auto-incrementing IDs).

·        Foreign Keys (FK):

o   Verifies that foreign key constraints are correctly defined and reference the appropriate parent tables.

o   Ordering: Penalizes if a table with a foreign key is defined before the table it references (e.g., the Sale table is defined before the Customer table).

·        Specific Column Requirements:

o   For the Car table, it specifically checks if the RegistrationID (or similar fuzzy name) column is defined as a VARCHAR with an appropriate length (penalizing VARCHAR(255) as too large).

·        Composite Primary Keys: For the OrdersProduct table, it checks for a composite primary key involving two columns.

 

For INSERT Statements:

 

·        Success Rate: Calculates a score based on the number of "successful" INSERT rows/statements out of a total expected (currently 235).

·        Column Count: Checks if the number of values provided in an INSERT statement matches the number of columns specified or implied by the table definition (excluding IDENTITY columns and specific calculated columns like Orders.Total and OrdersProduct.SubTotal).

·        Basic Data Type Validation:

o   Checks if numeric values are unquoted (or correctly quoted if they contain inner numeric content).

o   Ensures string values are properly quoted.

o   Validates DATETIME values to be either CONVERT(DATETIME, ...) functions or quoted date strings.

·        Ordering: Considers an INSERT statement unsuccessful if it attempts to insert data into a table that has a foreign key dependency on a table where no data has been inserted yet (based on the order of INSERT statements in the file).

·        Identity Column Insertion: Penalizes if an INSERT statement explicitly tries to provide a value for an IDENTITY column.

 

 

4. Limitations

 

·        Regex-Based Parsing: The SQL parsing relies heavily on regular expressions, which can be brittle and may not handle all complex, ambiguous, or non-standard SQL syntax variations.

·        No Database Execution: The grader parses and analyses the SQL code; it does not execute it against an actual database.  This means it cannot detect runtime errors, logical errors that only appear during execution, or performance issues.
